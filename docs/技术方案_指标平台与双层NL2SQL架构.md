# MES 智能问数系统 技术方案

## 一、方案概览

### 1.1 核心洞察

当前 NL2SQL 方案存在三个结构性缺陷：

| 维度 | 当前方案 | 改进后 |
|------|---------|--------|
| 架构层次 | 只有 Text-to-SQL 一层 | **双层：指标通道 + SQL 兜底** |
| 用户定位 | 隐含"全员可用" | **精准定位数据分析师** |
| 可靠性 | 没有量化目标 | **80% 查询走高可靠指标通道** |
| 工作量分配 | 70% 在 AI / 技术 | **60% 数据治理，30% 指标平台，10% NL2SQL** |

核心原则：**不要用 AI 解决一个可以用工程确定性解决的问题。** 高频、稳定、有明确口径的查询走指标层（100% 可靠），长尾、复杂、自定义的查询才走 Text-to-SQL。

### 1.2 方案定位

本方案不是替代现有 NL2SQL 系统，而是在其**前面加一层指标路由层**，形成双层架构：

```
用户查询 → 术语归一化 → 路由判断 → 指标通道（查视图，100%可靠）
                                    ↘ SQL通道（LLM生成，现有方案）
```

现有 NL2SQL 系统（LangGraph 工作流、BFS 图扩展、向量检索、Harness 飞轮）全部保留，作为 SQL 通道的基础设施。

## 二、双层架构设计

### 2.1 整体架构

```
                              ┌──────────────────────┐
                              │      用户输入         │
                              └──────────┬───────────┘
                                         ▼
                              ┌──────────────────────┐
                              │  代码节点：术语归一化  │  ← 精确字典匹配
                              │  + 参数提取（时间/产线 │
                              │    /料号/工序/供应商） │
                              └──────────┬───────────┘
                                         ▼
                              ┌──────────────────────┐
                              │     路由分发           │
                              └──────────┬───────────┘
                                    ┌────┴────┐
                                    ▼         ▼
                         ┌─────────────┐  ┌─────────────┐
                         │  指标通道    │  │   SQL通道    │
                         │  (查视图)    │  │ (LLM生成)    │
                         │  可靠性100%  │  │  当前方案    │
                         └──────┬──────┘  └──────┬──────┘
                                └────────┬────────┘
                                         ▼
                              ┌──────────────────────┐
                              │    格式化 + 返回      │
                              └──────────────────────┘
```

### 2.2 两层定位对比

| 维度 | 指标通道 | SQL 通道 |
|------|---------|----------|
| 适用场景 | 口径确定的高频查询 | 长尾、临时、复杂关联查询 |
| 查询来源 | 预定义 PostgreSQL 视图 | LLM 实时生成 SQL |
| 可靠性 | 100%（不经过 AI） | ~80%（取决于模型和数据质量） |
| 响应速度 | 毫秒级（直接查视图） | 秒级（LLM 生成 + EXPLAIN 校验） |
| 口径权威性 | 业务方书面确认后固化 | 无权威口径，每次生成可能不同 |
| 目标占比 | 上线 3 个月 > 60% | 上线 3 个月 < 40% |
| 维护成本 | 新增指标 = 新建视图 | 基于 Harness 飞轮持续优化 |

### 2.3 路由判断逻辑

```
normalize_status 输出四种状态：

├─ "matched"     → 单个指标命中，直接查对应视图，返回结果
├─ "ambiguous"   → 术语有歧义（如"合格率"对应多部门不同口径），返回追问
├─ "multi_match" → 多个指标同时匹配（用户一次问了多个问题），分段查询合并展示
└─ "no_match"    → 未匹配任何指标，走现有 NL2SQL 通道（SQL 兜底）
```

## 三、术语归一化方案

### 3.1 核心设计：精确字典，非向量检索

**结论：别名映射不放知识库，放代码节点里的精确字典。**

向量检索解决的是"模糊语义匹配"问题，而别名映射是精确查找问题。"良品率"对应 M004，这是确定性的。用向量检索反而引入不必要的模糊性和召回不稳定问题。

### 3.2 别名字典结构

```python
ALIAS_MAP = {

    "良品率": "M004",
    "合格率": "M004",

    "过站良品率": "M004",
    "制程良品率": "M004",

    # M005 首次通过率 FPY
    "首次通过率": "M005",
    "fpy": "M005",
    "首通率": "M005",
    "一次通过率": "M005",

    # M007 IQC合格率
    "iqc合格率": "M007",
    "来料合格率": "M007",
    "进料检验合格率": "M007",

    # M001 工单产量
    "工单产量": "M001",
    "日产量": "M001",
    "产量": "M001",
    "生产数量": "M001",

    # M003 在制工单
    "在制工单数": "M003",

    # ... 持续扩充
}
```

### 3.3 歧义术语处理

某些术语在不同部门口径不同，**不能直接映射，必须追问用户确认**：

```python
AMBIGUOUS_TERMS = {
    "合格率": {
        "conflict": True,
        "options": [
            {"id": "M004", "name": "过站良品率", "desc": "分母=过站SN总数，生产部口径"},
            {"id": "M007", "name": "IQC来料合格率", "desc": "分母=来料批次，质量部口径"},
            {"id": "M008", "name": "IPQC巡检合格率", "desc": "分母=巡检次数，质量部口径"},
            {"id": "M009", "name": "FQC成品合格率", "desc": "分母=检验数量，质量部口径"},
        ]
    }
}
```

### 3.4 匹配策略

- 使用**子串匹配**，天然不管用户词序（"今天良品率多少" 和 "良品率今天多少" 都能命中）
- 从**长到短**排序别名字典再匹配，避免短词覆盖长词（如"来料合格率"优先于"合格率"）
- 一句话命中多个指标 → 走 `multi_match`，分别查询视图后分段返回
- 容错：字典里加入常见截断词（如"品率"→M004）

### 3.5 字典维护机制

1. 每次 `status=no_match` 时，记录用户原始问题和最终 SQL 到日志表
2. 每周人工审核日志，发现反复出现的词且有明确对应指标 → 加进字典
3. 字典会越来越准，NL2SQL 负担越来越轻

## 四、动态参数提取与 SQL 拼装

### 4.1 设计原则

视图是固定口径的 SQL，但"今天""本周""A线"这些过滤条件每次不同，必须动态拼装。分两步：提取参数 → 拼装 SQL。

### 4.2 参数提取规则

| 参数类型 | 示例输入 | 提取方式 | 输出 |
|---------|---------|---------|------|
| 时间：今天 | "今天" "今日" "当天" | 关键词 + datetime 计算 | `date_start=今天的日期, date_end=今天的日期` |
| 时间：本周 | "本周" "这周" | 关键词 + timedelta | `date_start=周一, date_end=今天` |
| 时间：本月 | "本月" "这个月" | 关键词 + replace(day=1) | `date_start=1号, date_end=今天` |
| 时间：具体日期 | "2024-01-15" | 正则 `\d{4}[-/]\d{1,2}[-/]\d{1,2}` | `date_start=2024-01-15, date_end=2024-01-15` |
| 产线 | "A线" "SMT线" "A产线" | 正则 `[A-Za-z\d]+(线\|产线)` | `pdline=A线` |
| 料号 | "P001" "SKU-001" | 正则 `[A-Z]{1,4}[-_]?\d{3,}` | `part_no=P001` |
| 工序 | "贴片" "AOI" "ICT" | 正则匹配工序关键词 | `process=贴片` |
| 供应商 | "供应商XX" | 正则 `供应商[是为]?\s*["\u201c'"]?([^\s,，。]+)` | `supplier=XX` |
| 无时间词 | "良品率多少" | 默认兜底 | `默认近7天` |

### 4.3 指标-视图-参数映射配置

```python
METRIC_CONFIG = {
    "M004": {
        "view": "v_m004_yield_rate",
        "select": "产线名称, 工序名称, 统计日期, 通过数, 测试总数, 良品率_pct",
        "params": {
            "date_start": ("统计日期", ">="),
            "date_end":   ("统计日期", "<="),
            "pdline":     ("产线名称", "ILIKE"),
            "process":    ("工序名称", "ILIKE"),
        },
        "default_order": "统计日期 DESC, 良品率_pct DESC",
    },
    "M001": {
        "view": "v_m001_wo_daily_output",
        "select": "产线名称, 料号, 料号名称, 统计日期, 完工工单数, 计划总数量",
        "params": {
            "date_start": ("统计日期", ">="),
            "date_end":   ("统计日期", "<="),
            "pdline":     ("产线名称", "ILIKE"),
            "part_no":    ("料号", "="),
        },
        "default_order": "统计日期 DESC",
    },
    "M003": {
        "view": "v_m003_wip_count",
        "select": "产线名称, 料号, 料号名称, 在制工单数, 在制计划总量",
        "params": {
            "pdline":  ("产线名称", "ILIKE"),
            "part_no": ("料号", "="),
        },
        "default_order": "在制工单数 DESC",
    },
    "M007": {
        "view": "v_m007_iqc_rate",
        "select": "供应商名称, 料号, 料号名称, 统计月, 检验批次, 合格批次, IQC合格率_pct",
        "params": {
            "date_start": ("统计月", ">="),
            "date_end":   ("统计月", "<="),
            "supplier":   ("供应商名称", "ILIKE"),
            "part_no":    ("料号", "="),
        },
        "default_order": "统计月 DESC, IQC合格率_pct ASC",
    },
    "M011": {
        "view": "v_m011_stock",
        "select": "仓库名称, 料号, 料号名称, 正常库存, 冻结库存, 不良品库存, 总库存",
        "params": {
            "part_no": ("料号", "="),
            "pdline":  ("仓库名称", "ILIKE"),
        },
        "default_order": "总库存 DESC",
    },
    # ... 其余指标
}
```

### 4.4 完整执行示例

用户输入："今天A线良品率多少"

```
[术语归一化] → normalize("今天A线良品率多少")
  → 命中 "良品率" → metric_id = "M004"
  → extract_params → {date_start: "2026-06-05", date_end: "2026-06-05", pdline: "A线"}

[SQL拼装] → build_query("M004", params)
  → SELECT 产线名称, 工序名称, 统计日期, 通过数, 测试总数, 良品率_pct
    FROM v_m004_yield_rate
    WHERE 统计日期 >= '2026-06-05'
      AND 统计日期 <= '2026-06-05'
      AND 产线名称 ILIKE '%A线%'
    ORDER BY 统计日期 DESC, 良品率_pct DESC
    LIMIT 200

[执行] → HTTP 工具调用只读数据库接口
[格式化] → 表格化返回用户
```

## 六、数据治理前置条件

> 技术方案的正确性取决于数据治理的完成度。在指标视图上线前，以下工作必须先完成。

### 6.1 阶段 0：边界确认（1-2 周）

产出**项目边界确认书**，需要业务、IT、数据三方签字。必答问题：

1. 谁是第一批用户？列出具体姓名和岗位
2. 这些人现在怎么获取数据？
3. 最频繁的前 10 个查询问题是什么？→ 决定第一期指标范围
4. 哪个部门的数据最可信？从可信的开始做
5. "良品率"的计算口径由谁定义？生产部和质量部答案不同时谁说了算？
6. 现有报表的 SQL 是什么？→ 最宝贵的业务知识

### 6.2 阶段 1：元数据标注（4-6 周）

**优先标注顺序：** 生产核心链路 → 库存领料 → 质量检验 → 设备

每张表标注：中文名、业务含义、数据负责人、更新频率、数据质量评分、敏感字段

### 6.3 跨系统编码对齐

需要确认的具体问题：
- MES 的 `pdline_code` 和 ERP 系统的产线编码是否一致？
- 料号 `part_no` 在 MES 和 WMS 里格式是否相同？
- 供应商 ID 在各系统中是否同一套编码？

每发现一处不一致，需要建编码映射表，否则跨系统查询结果永远是错的。

### 6.4 业务术语标准化

产出《MES 业务术语标准手册》。关键口径必须书面确认：

- "完工"的定义：`wo_status='40'` 还是有入库记录？
- "良品率"的分母：投入数？完工数？检验数？
- "可用库存"：`正常库存 - 已分配数量` 还是只看 `qty`？
- OEE 计算公式采用哪个版本？
- 同一 SN 返工后重测，良品率取第一次还是最后一次？

## 七、视图部署策略

### 7.1 两步上线流程

```
第一步：开发库 / 测试库    第二步：生产库只读 Schema
┌─────────────────┐      ┌─────────────────────┐
│ 创建 v_m_* 视图   │ ──→ │ 口径确认书签字后      │
│ 业务方拿 Excel    │      │ 在生产库建视图        │
│ 比对数据是否正确   │      │ 前缀 v_m_ 区分业务表  │
│ 数字一致 → 签字   │      │ 只读账号查询          │
└─────────────────┘      └─────────────────────┘
```

### 7.2 关键决策：必须预先创建，不能用时创建

用时创建 SQL 视图在技术上可行，但等于把"口径确认"推迟到查询发生时——那时没有业务方在场，没人签字确认，结果出了问题找不到责任人。

预先创建视图的本质是一次**强制的口径确认仪式**。

## 八、与现有系统的集成方案

### 8.1 现有系统保留部分

| 组件 | 角色变化 |
|------|---------|
| LangGraph 工作流 | 只在 SQL 通道内使用 |
| BFS 图扩展 | 只在 SQL 通道内使用 |
| pgvector 向量检索 | 只在 SQL 通道内使用，不再参与术语归一化 |
| Harness 数据飞轮 | 保留，持续优化 SQL 通道 |
| 安全校验（SQL Validator） | 保留 |
| EXPLAIN 校验与修复 | 保留 |

### 8.2 新增部分

| 组件 | 说明 |
|------|------|
| 术语归一化代码节点 | Python 精确字典匹配 + 参数提取 |
| 指标路由节点 | 根据 `normalize_status` 分发到指标通道或 SQL 通道 |
| 指标视图查询节点 | 拼装参数化 SQL → HTTP 调用只读数据库 |
| 歧义追问节点 | 当 `ambiguous` 时向用户返回追问消息 |
| 指标视图集合 | 17 个 PostgreSQL 视图，部署在 MES 业务库只读 Schema |

### 8.3 Dify 工作流示意

```
START
  ↓
[代码节点: 术语归一化 + 参数提取]
  ↓
[条件分支: normalize_status]
  ├─ "matched"      → [代码节点: SQL拼装] → [HTTP工具: 查视图] → [格式化输出] → END
  ├─ "ambiguous"    → [追问消息] → END (等用户选择后重入)
  ├─ "multi_match"  → [循环: 逐指标查视图] → [合并输出] → END
  └─ "no_match"     → [现有NL2SQL工作流] → END
```

## 九、别名字典维护与迭代

### 9.1 未匹配日志

每次 `status=no_match` 时，写入日志表：

```sql
CREATE TABLE nl2sql_unmatched_log (
    id          SERIAL PRIMARY KEY,
    user_query  TEXT NOT NULL,           -- 用户原始输入
    final_sql   TEXT,                    -- 最终生成的 SQL
    channel     VARCHAR(20) DEFAULT 'sql', -- 走哪个通道
    created_at  TIMESTAMP DEFAULT NOW()
);
```

### 9.2 迭代流程

```
每周审计一次未匹配日志
  → 发现反复出现的关键词
  → 判断是否对应已有指标
  → 是 → 加入 ALIAS_MAP
  → 否 → 评估是否需要新建指标
  → 版本更新，灰度上线
```

## 十一、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 业务部门不愿交出数据解释权 | 指标口径无法确认 | 从无争议指标开始；让业务方定义口径、IT 实现；先给数据不做考核 |
| 数据质量差，视图结果不准 | 用户不信任系统 | 先从数据最可信的部门开始；视图上线前和现有报表逐条比对 |
| 别名字典覆盖不足 | 大量查询走 SQL 通道 | 每周审计未匹配日志，快速迭代扩充字典 |
| 产线/料号编码不统一 | 跨系统查询结果错误 | 阶段 1 重点排查编码对齐问题，建立编码映射表 |
| 4 处待确认字段无法确认 | 对应视图无法上线 | 先上线已确认的 13 个视图，待确认的推迟到二期 |
