# MES 数据治理 + 指标平台 完整实施方案

## 先说清楚整体逻辑

这不是一个技术项目，是一个**以数据治理为主体、以指标平台为载体、以NL2SQL为入口**的工程。
三件事的工作量比例是：数据治理60% / 指标平台建设30% / NL2SQL调优10%。

顺序不能反：治理不做好，指标口径就争不清；指标口径争不清，高频查询就没法固化；
高频查询没固化，NL2SQL就要承担所有不确定性，准确率永远上不去。

---

## 阶段0：开工前必须搞清楚的问题（1~2周，不写代码）

这个阶段的产出是一份**项目边界确认书**，要求业务、IT、数据三方签字。

**要问清楚的问题：**

1. 谁是第一批用户？列出具体姓名和岗位。不接受"各部门都要用"这种答案。
2. 这些人现在怎么拿数据？Excel导出？找IT出报表？直接看系统？
3. 他们最频繁问的前10个问题是什么？把这10个问题写下来，这就是指标平台第一期的范围。
4. 哪个部门的数据最脏？哪个部门的数据最可信？从可信的开始做。
5. 谁有权定义"良品率"的计算口径？如果生产部和质量部的答案不同，谁说了算？
6. 现在MES系统有没有在跑的报表？那些报表的SQL是什么？这是最宝贵的业务知识。

**为什么必须先做这步：**
我从你的数据库里找到了86张适合指标化的表，但我不知道哪10个指标是你们业务方
真正关心的。技术人员来定指标口径是这类项目失败的头号原因。

## 阶段1：元数据标注（4~6周，核心治理工作）

### 1.1 建立标注工作台

不要用Excel，用一个简单的Web表单（可以用Notion/飞书多维表格代替）。
每张表对应一条记录，包含以下字段：

| 字段 | 内容 | 填写人 |
|------|------|--------|
| 表名 | t_pd_sn_travel | 系统自动 |
| 中文名 | SN过站履历 | IT |
| 业务含义 | 记录每个SN经过每道工序时的结果... | 业务骨干 |
| 数据负责人 | 张三（生产部） | 业务负责人 |
| 更新频率 | 实时（每次过站写入） | IT |
| 数据质量评分 | 4/5（偶有重复过站记录） | IT+业务 |
| 使用场景 | SN追溯、工序良品率统计 | 业务骨干 |
| 敏感字段 | operator（操作人） | 业务负责人 |
| 是否可对外查询 | 是，但operator字段需脱敏 | 业务负责人 |

**优先标注顺序：**
1. 第一批：t_pd_wo / t_pd_sn_status / t_pd_sn_travel / t_pd_sn_defect（生产核心链路）
2. 第二批：t_wms_stock / t_wms_wo_material_bill系列（库存领料）
3. 第三批：t_qm_inspect_info系列（质量检验）
4. 第四批：t_ems_equipment系列（设备）
5. 其余表按需补充

你的数据库里有大量无注释的表（如t_wms_po_in_bill_detail等），
这些表的业务含义只能由懂业务的人填，程序猜不了。

### 1.2 字段级口径标注（最难、最值钱的部分）

对核心指标相关的字段，必须标注清楚：

```yaml
# 示例：t_pd_sn_travel.pass_flag 的口径定义
field: pass_flag
table: t_pd_sn_travel
type: varchar
enum_values:
  Y: 过站通过（含让步接收）
  N: 过站不通过，需返工或报废
business_rule:
  - 同一个SN在同一道工序可能有多条记录（返工后重测）
  - 统计良品率时应取最终一条记录（max(create_time)）
  - 不包含skip工序的记录（skip_flag=1的行不计入分母）
owner: 质量部 李四
confirmed_date: 2024-01-15
```

这份口径定义文件是整个项目最重要的产出，
比任何代码都重要。没有它，指标平台算出来的数字没人敢信。

### 1.3 跨系统编码对齐

你的MES里用 pdline_code 表示产线。
需要确认：

- MES的pdline_code 和 ERP系统的产线编码是否一致？
- 料号：MES的part_no 和 采购系统的物料编码格式是否相同？
- 供应商：MES的supplier_id 和 ERP/财务系统的供应商编码是否同一套？

每发现一处不一致，就需要建一张**编码映射表**，
否则跨系统的数据关联查询结果永远是错的。

## 阶段2：业务术语标准化（与阶段1并行，3~4周）

### 2.1 建立MES业务词典

把以下问题的答案，逐条书面确认并存档：

**生产域**
- "完工"的定义：wo_status='40'，还是有入库记录，还是两者都要？
- "在制"的定义：包不包括暂停的工单（wo_status='30' only，还是'20'+'30'）？
- "计划达成率"的分子分母：计划数量用plan_qty，实际数量用什么字段？
- "投入数"的定义：工单下达数量，还是实际上线SN数？

**质量域**
- "良品率"的分母：是投入数、还是完工数、还是检验数？
- "不良率"和"良品率"加起来等于100%吗？（如果有让步接收，不一定）
- IPQC和FQC的良品率算法相同吗？
- "首次通过率"（FPY）的定义：第一次测试即通过的SN数/总SN数

**库存域**
- "可用库存"的定义：正常库存 - 已分配数量，还是只看t_wms_stock.qty？
- "冻结库存"是否算入"总库存"？
- 在途库存算不算库存？

**设备域**
- OEE的计算公式：你们采用哪个版本的定义？
- "计划停机"包含哪些情况？影响OEE分子分母

把这些答案整理成一份**《MES业务术语标准手册》**，
所有人看到"良品率"三个字，必须查这本手册，不能自己理解。

## 阶段3：指标平台建设（6~8周）

### 3.1 指标分层设计

指标分三层，从下往上建：

```
原子指标（不可再拆）
  → 派生指标（原子指标的加工）
    → 复合指标（多个派生指标的组合）
```

**以良品率为例：**
```yaml
# 原子指标
atom_metric:
  id: M001
  name: 过站通过数
  sql: |
    SELECT pdline_code, DATE(create_time) AS dt, COUNT(*) AS pass_count
    FROM t_pd_sn_travel
    WHERE pass_flag = 'Y'
      AND skip_flag != 1  -- 排除skip工序
    GROUP BY pdline_code, DATE(create_time)

atom_metric:
  id: M002
  name: 过站总数（分母）
  sql: |
    SELECT pdline_code, DATE(create_time) AS dt,
           COUNT(DISTINCT sn) AS total_count  -- 去重，同SN返工不重复计
    FROM t_pd_sn_travel
    WHERE skip_flag != 1
    GROUP BY pdline_code, DATE(create_time)

# 派生指标
derived_metric:
  id: M003
  name: 产线日良品率
  formula: M001.pass_count / M002.total_count
  dimensions: [pdline_code, dt, process_code]
  filters:
    - 时间范围（默认今日）
    - 产线（可选，默认全部）
    - 工序（可选）
  owner: 质量部
  confirmed_date: 2024-01-15
```

### 3.2 你的MES数据库里，第一期应该固化的指标清单

基于数据库分析，以下指标应该优先做，因为所需字段明确、口径争议小：

**生产类（t_pd_域）**
- M001 工单日产量（按产线、料号）
- M002 工单计划达成率（实际完工/计划数量）
- M003 在制工单数（实时）
- M004 SN过站良品率（按产线、工序、日期）
- M005 SN首次通过率FPY
- M006 工单平均周期时间（从下达到完工）

**质量类（t_qm_域）**
- M007 IQC来料合格率（按供应商、料号）
- M008 IPQC巡检合格率（按产线）
- M009 FQC成品合格率（按料号）
- M010 TOP N不良类型（按时段、产线）

**库存类（t_wms_域）**
- M011 实时库存（按料号、仓库）
- M012 当日领料量（按工单、料号）
- M013 库存周转天数（需结合出库数据）
- M014 采购到货准时率

**设备类（t_ems_域）**
- M015 设备月故障次数（按设备、类型）
- M016 平均维修时长MTTR（按设备型号）
- M017 设备点检完成率

### 3.3 指标平台的技术实现（务实版）

不要过度设计。在你们当前阶段，指标平台的最小实现是：

**选项A（推荐，低成本）：SQL视图 + 参数化查询**
把每个指标的SQL写成PostgreSQL视图，Dify的Text-to-Metrics直接查视图，
不经过LLM生成SQL，可靠性100%。

```sql
-- 创建产线日良品率视图
CREATE VIEW v_metric_yield_rate AS
SELECT
  pl.pdline_name,
  st.pdline_code,
  DATE(st.create_time) AS dt,
  COUNT(DISTINCT CASE WHEN st.pass_flag='Y' THEN st.sn END) AS pass_count,
  COUNT(DISTINCT st.sn) AS total_count,
  ROUND(
    COUNT(DISTINCT CASE WHEN st.pass_flag='Y' THEN st.sn END)::numeric
    / NULLIF(COUNT(DISTINCT st.sn), 0) * 100, 2
  ) AS yield_rate_pct
FROM t_pd_sn_travel st
LEFT JOIN t_bd_pdline pl ON st.pdline_code = pl.pdline_code
WHERE st.skip_flag != 1
GROUP BY pl.pdline_name, st.pdline_code, DATE(st.create_time);
```

用户说"今天A线良品率"，系统直接：
```sql
SELECT * FROM v_metric_yield_rate
WHERE dt = CURRENT_DATE AND pdline_name = 'A线';
```

不经过任何LLM，结果100%可预测。

**选项B（中期，有条件时）：独立指标计算服务**
把指标SQL抽成Python服务，定时跑（每小时/每天），结果存ClickHouse，
查询走ClickHouse而不是实时查PostgreSQL。
好处：查询快、不影响MES生产系统性能。
前提：数据量达到实时查询瓶颈时再考虑。

**选项C（不推荐在这个阶段做）：完整指标平台（DataBricks/DBT等）**
工具链复杂，运维成本高，在指标数量<50个时完全不需要。

## 阶段4：Dify工作流接入指标平台（2~3周）

这时候才回到Dify。工作流增加一个路由层：

```
用户输入
   ↓
[路由节点] ← LLM判断：这个问题能用指标回答吗？
   ↓              ↓
[指标查询]    [Text-to-SQL]
（查视图）    （走之前的方案）
   ↓              ↓
[格式化输出] ← ← ← ←
```

路由节点的Prompt：
```
判断用户问题是否属于以下已定义指标之一，如果是，输出对应指标ID和参数；
如果不是，输出 {"type": "sql", "reason": "不在指标范围内"}

已定义指标：
M001 工单日产量 - 参数：产线(可选)、日期范围(可选)
M003 在制工单数 - 参数：产线(可选)、料号(可选)
M004 SN过站良品率 - 参数：产线(可选)、工序(可选)、日期范围(可选)
M007 IQC来料合格率 - 参数：供应商(可选)、料号(可选)、日期范围(可选)
M011 实时库存 - 参数：料号(必填)、仓库(可选)
...（其余已定义指标）

用户问题：{{question}}

输出JSON格式：
{"type": "metric", "id": "M004", "params": {"pdline": "A线", "date": "today"}}
或
{"type": "sql", "reason": "问的是SN具体的过站时间，不在指标范围"}
```

## 阶段5：组织协同（贯穿全程，最难的部分）

这不是技术问题，直接说怎么操作。

**数据解释权问题的实质：**
生产部门不愿意让你定义"良品率"，因为一旦口径固定了，他们的数字就可以被
随时查随时质疑，绩效数字的水分空间就消失了。这是合理的自我保护，不是无理取闹。

**破局方法：**

1. **不要从敏感指标开始**。第一期选那些没有争议的、所有人都希望看清楚的指标，
   比如"实时在制工单数"——这个没有绩效敏感性，生产部门自己也想知道。

2. **让业务方定义口径，你负责实现**。
   指标口径定义书必须由业务方起草、IT确认技术可行性，然后双方签字。
   不是IT告诉业务"良品率应该这么算"，而是业务告诉IT"我们定义良品率是这样的，你帮我实现"。

3. **先给数据，不拿数据做考核**。
   上线初期，指标查询结果只给到数据分析师，不直接接入绩效系统。
   等数据质量稳定、口径争议平息之后，再讨论是否接入考核。
   这一点要明确承诺给各业务部门，降低他们的防御心理。

4. **用数据暴露问题，而不是用问题攻击部门**。
   当数据显示某产线良品率偏低时，分析师的工作是"帮这个产线找原因"，
   而不是"拿这个数据找这个产线的领导算账"。
   这个定位要从项目一开始就说清楚。

5. **找一个有数据意愿的业务部门先跑通**。
   通常质量部门或运营部门对数据可视化需求最强，最愿意配合治理。
   先帮他们把数据做好，让他们的工作效率提升，形成示范效应，
   再推动其他部门跟进。

## 判断项目是否走在正轨上的检查项

每月检查一次：

- [ ] 新增了多少条字段口径定义？（健康值：每月>20条）
- [ ] 有多少个指标被业务方书面确认口径？（第一期目标：17个全部确认）
- [ ] 用户对指标查询结果提出异议的次数？（下降趋势才是正轨）
- [ ] 路由到指标层的查询占比？（目标：3个月后>60%，6个月后>80%）
- [ ] 有多少张表完成了元数据标注？（每月>20张）
- [ ] 有没有发现跨系统编码不一致的问题？发现几个、解决几个？

如果"用户对结果提出异议的次数"没有下降，说明口径治理没有推进，
这时候增加任何AI功能都是在浪费时间。
